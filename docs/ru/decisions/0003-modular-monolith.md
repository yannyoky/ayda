# 0003. Модульный монолит

[English](../../decisions/0003-modular-monolith.md) · Русский

## Контекст
Один разработчик, горстка пользователей на старте и основной цикл (чек-ин, квесты, подтверждение, лента, лестница), который затрагивает почти все домены. Микросервисы добавили бы сетевые вызовы, распределённые транзакции, отдельные деплои и мониторинг для каждого сервиса, не решая пока никакой реальной проблемы.

## Решение
Бэкенд - одно развёртываемое приложение, разделённое на доменные модули в `backend/src/ayda/modules/`: auth, quests, assistant, events, social, chat, habits, analytics. Каждый модуль владеет своими таблицами и логикой. Модули не импортируют друг друга; это проверяет import-linter в CI. Взаимодействие между модулями идёт через общий прикладной код и доменные события (они также пишутся в append-only таблицу `events`). Фоновый воркер запускает тот же код с другой точкой входа. Centrifugo и PostgreSQL - отдельная инфраструктура, а не наши сервисы.

## Последствия
Простой деплой и транзакции в пределах основного цикла. Модуль выносится в отдельный сервис, только когда профиль его нагрузки становится действительно другим (например, ассистент переезжает на хост с GPU); чёткие границы делают это переносом, а не переписыванием. Контракт import-linter позже можно ослабить и разрешить импорт публичного API модуля, если прямые вызовы окажутся проще.
