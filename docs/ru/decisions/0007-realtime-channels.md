# 0007. Realtime через один персональный канал Centrifugo на пользователя

[English](../../decisions/0007-realtime-channels.md) · Русский

## Контекст
В M2 появляются личные сообщения между друзьями (US-17) и совместные квесты с общим чатом (US-18). ADR 0002 выбрал Centrifugo для realtime. Сообщение должно дойти до открытого чата в течение секунды, в списке чатов нужны живые счётчики непрочитанного, история должна переживать обрыв соединения, а пользователь может получать только то, к чему он относится. Бывший друг должен сразу перестать получать сообщения из личного чата, а пользователь может состоять во многих чатах.

Рассматривались две схемы каналов:
- **Канал на каждую беседу** (`chat:<id>`) с токенами подписки. Чтобы список чатов оставался живым, клиент подписывается на каждую беседу, и у пользователя с 30 чатами 30 подписок и 30 токенов. Доступ решается при выдаче токена, поэтому после удаления из друзей бывший друг остаётся подписан, пока токен не истечёт.
- **Один персональный канал на пользователя** (`personal:#<user id>`). Бэкенд публикует каждое событие в персональные каналы текущих участников беседы (Centrifugo `broadcast`). Каналы Centrifugo с ограничением по пользователю (граница `#`) позволяют подписаться только соединению, в токене которого указан этот user id, поэтому токены подписки не нужны.

## Решение
- Один персональный канал на пользователя, `personal:#<user id>`, в namespace `personal` с `allow_user_limited_channels`, историей из 100 публикаций на 1 час и `force_recovery`.
- API выдаёт короткоживущий токен соединения (HS256 JWT, `sub` = user id, 1 час) по `POST /realtime/token`; клиент обновляет его тем же вызовом. HTTP API key Centrifugo и секрет токенов берутся из переменных окружения.
- Путь записи: API сохраняет сообщение в PostgreSQL и делает commit, затем рассылает его в персональные каналы участников. Если Centrifugo недоступен, задача `realtime.publish` повторяет рассылку, поэтому сообщение никогда не теряется и в худшем случае приходит с опозданием.
- События - небольшие JSON-объекты с полем `type` (`message.created`, `message.deleted`, `conversation.read`, позже `coop.updated`), описанные в `contracts/openapi.yaml` как `RealtimeEvent`. Источником истины остаётся REST API: после переподключения, которое Centrifugo не может восстановить (больше 1 часа или 100 событий), клиент заново загружает беседы и сообщения через REST.
- Доступ проверяется только на пути записи: бэкенд решает, кто получит каждое событие. Удаление из друзей сразу закрывает личный чат для новых сообщений, потому что бывшему другу больше ничего не публикуется.

## Последствия
Одна подписка на клиента держит живыми список чатов, счётчики непрочитанного и обновления совместных квестов. Восстановление после коротких обрывов берёт на себя Centrifugo; при длинных перерывах клиент возвращается к страницам REST. Текст сообщений проходит через in-memory историю Centrifugo на том же российском VPS не дольше часа и не пишется в его логи. Для масштабирования за пределы одного узла Centrifugo понадобится его Redis engine, но это далеко за пределами нагрузки MVP. Токен подписки на канал всё ещё можно добавить позже для каналов, общих для многих пользователей (например, публичного чата события).
