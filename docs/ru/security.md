# Секреты и проверки на утечки

[English](../security.md) · Русский

Секреты хранятся только в переменных окружения (`.env` на сервере, секреты GitHub Actions в CI). В репозиторий они не попадают никогда. Ошибку ловят три уровня защиты.

## 1. gitleaks в CI

Workflow `Secrets` (`.github/workflows/secrets.yml`) запускает [gitleaks](https://github.com/gitleaks/gitleaks) на каждый pull request и каждый push в `main`. Он проверяет всю историю git, а не только новые коммиты, и роняет проверку, если находит что-то похожее на ключ, токен или пароль. Находки выводятся в скрытом виде.

## 2. Локальный pre-commit хук

Хук останавливает коммит ещё до того, как он уйдёт с компьютера. Установить один раз на каждую копию репозитория (одинаково в Windows PowerShell, macOS и Linux):

```powershell
uv tool install pre-commit
pre-commit install
```

После этого каждый `git commit` проверяет добавленные изменения. Первый запуск скачивает и собирает gitleaks, это занимает около минуты. Проверить всё рабочее дерево вручную:

```powershell
pre-commit run gitleaks --all-files
```

Если gitleaks уже установлен как программа (`winget install Gitleaks.Gitleaks`), `gitleaks git .` проверяет историю так же, как CI.

## 3. Secret scanning и push protection в GitHub

GitHub проверяет пуши на форматы токенов известных сервисов (Telegram, Cloudflare, Groq, ключи S3 в стиле AWS и многие другие). Для публичного репозитория это бесплатно. Как включить:

1. Открыть репозиторий на GitHub, затем **Settings**.
2. В левом меню открыть **Advanced Security** (в старом интерфейсе: **Code security and analysis**).
3. В разделе **Secret Protection** (или **Secret scanning**) нажать **Enable**.
4. Чуть ниже включить **Push protection**. Тогда GitHub отклонит `git push` с распознанным секретом и покажет файл и строку.
5. По желанию на той же странице: **Private vulnerability reporting**, чтобы люди могли сообщить об уязвимости без публичного issue.

Предупреждения появляются в **Security → Secret scanning**.

## Ложные срабатывания

Фиктивное значение, которое должно остаться в коде (тестовые данные, пример из документации сервиса), помечается комментарием `# gitleaks:allow` на той же строке. Находка в старом коммите, который уже не изменить, добавляется в `.gitleaksignore` как fingerprint (`commit:file:rule:line`, gitleaks его печатает). Настоящий секрет так разрешать нельзя.

## Токен Telegram-бота

Токен боевого бота служит мастер-ключом: кто его знает, тот может подписать Telegram `initData` любого пользователя и войти в любой аккаунт. Он лежит только в `/opt/ayda/.env` на сервере и в защищённом окружении `production`, но никогда в секретах уровня репозитория, которые читает любой workflow из `main`. Еженедельные Live checks используют отдельного тестового бота (`TELEGRAM_TEST_BOT_TOKEN`; без него проверка Telegram пропускается).

Если токен мог утечь: в @BotFather отправить `/revoke` и выбрать бота, записать новый токен в `TELEGRAM_BOT_TOKEN` в `/opt/ayda/.env` (и в окружение `production`, если он там есть) и запустить workflow Deploy. Старый токен сразу перестаёт работать, и любой `initData`, подписанный им, отклоняется. Уже выданные сессии остаются в силе; если в аккаунты могли зайти, завершите их все: запишите новый `AUTH_TOKEN_SECRET` в `.env` (им подписаны access-токены) и отзовите refresh-токены:

```sh
docker compose -f docker-compose.prod.yml exec postgres psql -U ayda -d ayda \
  -c "update auth.refresh_tokens set revoked_at = now() where revoked_at is null"
```

После этого все входят заново.

## Если секрет всё-таки утёк

1. Сначала отозвать или заменить секрет у сервиса (`/revoke` в BotFather, API-токены Cloudflare, ключи S3 в Beget и так далее). Секрет, запушенный в публичный репозиторий, считается известным всем, даже если коммит потом удалить.
2. Записать новое значение в `/opt/ayda/.env` на сервере или в секрет GitHub Actions и перезапустить нужные контейнеры.
3. Убрать значение из кода обычным коммитом. Переписывать историю не обязательно, и это не заменяет шаг 1.
